# 실사용 검증

## 완료

- macOS 26.6 Apple Silicon에서 릴리스 컴파일.
- `.app` 패키지 생성, Info.plist 검사, ad-hoc 코드 서명 검증.
- 핵심 검사: 창별 MRU, 관찰하지 못한 창의 안정 정렬, 종료 창 제거, PID 구분, 정·역방향 선택, 엄격한 캐시 예산, 이미지 참조 해제, 1,000개 4K 창의 비용 처리, 세션 무효화와 캡처 동시성.
- 사용자가 메뉴 막대 아이콘과 진단 복사를 확인함.
- 시스템 설정에서 ScreenTap 접근성·화면 기록 허용 상태를 확인함.
- 0.1.1 사용자 실측: 마지막 캡처 시점 134.8MiB, 전환기 종료 후 43.1MiB, 종료 후 썸네일 캐시 0바이트.
- 페이지 창 요청/매칭/캡처 성공/실패: 12/12/12/0, OS 캡처 오류 없음.
- 사용자가 실제 썸네일 표시와 여백 클릭 후 Option 해제 시 전환 취소를 확인함.
- 0.1.1 자동 검사 16개 통과.
- 0.2.0: 실제 앱과 마케팅 이미지가 공유하는 렌더러의 썸네일 픽셀 출력, macOS의 ICNS 디코딩 검사를 더해 총 18개 통과.
- 0.2.0 GUI 실행 상태는 별도 사용자 확인 대상이며, 0.1.1 측정치를 새 버전 실측으로 간주하지 않음.

## 기능 검사

1. Chrome 창 두 개, 터미널 창 두 개, Slack, Calendar를 연다.
2. Chrome A → 터미널 B → Slack → Chrome B 순서로 실제 창을 사용한다.
3. Option을 누른 채 Tab을 누른다. 좌상단부터 Chrome B, Slack, 터미널 B, Chrome A 순인지 확인한다.
4. 처음 선택은 직전 창이어야 한다. Tab 반복·Shift-Tab·화살표·Esc·Return·마우스 클릭을 확인한다.
5. 같은 앱의 두 창 제목을 같게 만들어도 선택한 개별 창으로 이동하는지 확인한다.
6. 숨김·최소화·전체 화면·다른 Space·다중 디스플레이를 각각 확인한다. 이미지를 얻지 못한 창은 아이콘 대체를 허용하되 실제 전환 성공 여부는 별도로 기록한다.
7. 12개보다 많은 창을 열고 빠르게 페이지를 넘긴 뒤 이미지와 선택이 뒤섞이지 않는지 확인한다.
8. 한국어·영어 전환, 화면 기록 거부, 접근성 거부 후 복구를 확인한다.

## 메모리 검사

메뉴의 ‘메모리 진단 복사’는 해당 프로세스의 `phys_footprint`를 읽는다. 새로 실행한 다른 프로세스에서 측정하는 방식이 아니다.

1. 시작 후 1분 대기 → 진단 복사.
2. 메뉴에서 ‘창 전환기 열기’ → 이미지 로딩 후 Esc로 닫고 진단 복사. `Last page requested/matched/captured/failed`, `Last raw image`, `Last preview footprint`, `Last capture error`에서 마지막 캡처 상태를 확인한다. 화면이 열린 순간의 전체 메모리는 활성 상태 보기에서 별도로 측정한다.
3. Esc로 닫기 → 5초 후 진단 복사. 썸네일 바이트가 0인지 확인한다.
4. 전환기를 100회 열고 닫고, 5분 후 다시 측정한다.
5. 최소 30분 사용하고 재측정한다. 반복할 때마다 메모리가 계속 증가하는지 본다.
6. 활성 상태 보기에서 WindowServer의 메모리 변화도 함께 기록한다.
7. 동일한 창·해상도·디스플레이·미리보기 설정으로 AltTab과 따로 실행해 비교한다.

현재 기록:

| 상태 | 프로세스 메모리 | 썸네일 바이트 | 비고 |
|---|---:|---:|---|
| 캡처 프레임워크 초기화 전 대기 (0.1.0) | 14.1MiB | 0 | 사용자 제공, macOS 26.6 |
| 마지막 캡처 시점 (0.1.1) | 134.8MiB | 미수집 | 사용자 제공, 전체 피크 측정 아님 |
| 전환기 종료 후 (0.1.1) | 43.1MiB | 0 | 사용자 제공 |
| 100회 반복 후 | 미측정 | 미측정 | 안정화 시간 포함 |
| 30분 사용 후 | 미측정 | 미측정 | 지속 증가 여부 확인 |

`--diagnostics`는 GUI 없이 시작한 별도 프로세스의 기본 메모리만 출력하므로 실제 앱 메모리의 대체 측정으로 사용하지 않는다. `--preview`와 `--render-preview`는 합성 데이터 기반 레이아웃 점검용이며 실제 창 캡처 검증으로 간주하지 않는다.

- GitHub 업로드와 Pages 공개는 성공 응답을 확인하기 전까지 완료로 간주하지 않음.

## 0.2.1 권한 흐름 확인

- 앱 시작 시 접근성 미허용 상태에서 이벤트 탭을 만들지 않음.
- 허용 버튼 → 앱 확인 시트 → 거부는 설정 열기 없음, 허용은 설정 URL 한 번만 열기.
- `AXIsProcessTrustedWithOptions(prompt: true)`와 `CGRequestScreenCaptureAccess`를 설정 열기와 함께 호출하던 중복 제거.
- 권한 안내가 보이는 동안 0.5초마다 비요청 확인 API로 재확인. 창을 닫으면 타이머 제거.
- 접근성 허용 시 창 관찰·키보드 탭 연결, 회수 시 관찰·탭 제거, 다시 허용 시 재연결.
- 화면 기록 반영 후 필요한 경우 열린 전환기의 미리보기를 다시 로드.
- 새 프로세스 실행이 성공했을 때만 이전 프로세스를 종료하는 재시작 버튼 제공.
- GUI 확인 필요: 실제 macOS 권한을 바꾼 뒤 상태 갱신, 파란 허용·일반 거부 시트, 설정창 단일 열기, 재시작 복구. 자동 핵심 검사 통과를 시스템 권한 UI의 실기기 검증으로 간주하지 않음.


## 0.2.2 권한 등록 회귀 수정

0.2.1의 설정 URL만 여는 흐름은 앱의 권한 목록 등록 요청을 대신하지 못한다.
이를 수정하여 사용자 허용 확인 후 ScreenCaptureKit 콘텐츠 조회 또는 AX 요청을
한 번 보내고, 설정 열기는 별도의 명시적 후속 클릭으로만 처리한다.

`PermissionRequests`의 OS 요청·설정 열기 콜백을 테스트 대역으로 실행해 다음을 검사:

- 거부는 OS 요청과 설정 열기를 모두 실행하지 않음. 이후 허용은 실제 요청을 실행.
- 첫 허용은 요청 한 번, 설정 열기는 0번. 다음 명시적 클릭에서만 설정을 열기.
- 접근성과 화면 기록은 독립적으로 요청.
- 반복 클릭에도 네이티브 요청은 한 번만 유지.

기존 18개 검사에 4개를 추가했다. 실제 macOS TCC 목록과 시스템 팝업 표시는
시스템 환경에서 별도 확인할 항목이며 모의 콜백 검사로 검증했다고 주장하지 않는다.

프로젝트 폴더 이름 변경 후 이전 절대 경로가 들어 있는 Swift 모듈 캐시가
발견되어 생성된 `.build` 캐시를 지운 뒤 새 경로에서 다시 빌드했다.
